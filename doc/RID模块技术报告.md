## 1. 项目概述

### 1.1 项目背景

根据国标 GB 46750-2025《民用无人驾驶航空器系统运行识别规范》（2026-05-01 起实施），所有无人机在飞行过程中必须**持续向外广播运行识别信息**（包括唯一识别码、位置、高度、速度、航向、运行状态等）。为满足该要求，本项目基于 ESP32-S3 为公司编队无人机自研了一套**广播式运行识别发送模块**，并配套现场检测工具用于验收与合规自查。

### 1.2 交付成果

| 成果 | 说明 |
|------|------|
| 硬件模块 | 基于 ESP32-S3 的广播式 RID 模块，USB 直连飞控，BLE 5 扩展广播 |
| 固件 | 完整 firmware，覆盖 GB 46750 全部 21 项数据字段 |
| PC 检测软件 | `RIDCheck.exe`——BLE 抓包、逐字段解码、合规判定、飞行日志导出 |
| 安卓检测 APP | `RID检测` v1.7——现场 BLE 抓包、合规判定、Word 报告导出、csv抓包日志导出 |
| 测试套件 | 固件侧 8303 例 + PC 端 28 例 + 安卓端 63 例，全部通过 |

## 3. 技术方案

### 3.1 硬件配置

| 部件 | 配置 | 说明 |
|------|------|------|
| 主控 | ESP32-S3（8MB Flash） | 满足飞行日志 ≥ 120h 存储需求（实测约 170h） |
| 广播链路 | BLE 5 Extended Advertising（NimBLE 协议栈） | 设备名 `GBI_RID_001`，Service UUID `0x0D50`，GB 版本字节 `0x20` |
| 数据源 | USB Host（GPIO19/20，CDC-ACM） | 直连飞控 USB 口，只读模式读取 MAVLink 数据 |
| 状态指示 | WS2812B RGB LED（GPIO48，RMT 驱动） | 详见表 3.1 |
| 调试/导出 | UART0 | 调试输出 + 飞行日志串口导出 |

**表 3.1 LED 状态指示（GB 46750-2025, 5.1.5）**

| 状态 | LED 行为 | 含义 |
|------|----------|------|
| STANDBY | 绿色慢闪（0.5Hz） | 地面待机，模块自检通过 |
| BROADCASTING | 蓝色快闪（2.5Hz） | 空中/紧急状态，正在广播 |
| DEGRADED | 橙色快闪（~1.7Hz） | 自修复后降级运行 |
| FAULT | 红色常亮 | 模块故障，三级自修复全部失败 |

### 3.2 固件分层架构

固件按职责拆分为五层，数据自上而下逐层处理，层间通过明确的数据接口通信：

```
飞控 USB ──→ USB Host (CDC-ACM) ──→ MAVLink 解析器 ──→ FlightData
                                                              │
                                                              ▼
                                                     RIDBroadcastManager.update()
                                                              │
                                         ┌──────────┬─────────┼──────────┬──────────┐
                                         ▼          ▼         ▼          ▼          ▼
                                      数据校验   包构建    广播调度   飞行日志    LED 指示
```

| 层次 | 目录 | 职责 |
|------|------|------|
| 协议层 | `protocol/` | 将飞行数据按 GB 46750 编码为广播报文（21 字段，M 字段恒在） |
| 数据层 | `data/` | 通过 USB Host 读取飞控 MAVLink 数据，解析出位置/速度/航向/状态等 |
| 编排层 | `broadcast/` | 整条流水线调度：数据校验 → 组包 → 广播 → 日志，承载状态机、自检、自愈 |
| 传输层 | `broadcaster/` | BLE 5 扩展广播，三级自愈（原地重启 → PHY 切换 → 整体重初始化） |
| 交联层 | `interlink/` | 飞控安全通知的抽象接口，量产时替换为真实后端 |

辅助模块：`indicators/`（LED 控制）、`logging/`（飞行日志 + 故障记录）、`console/`（UART 命令行）、`telemetry/`（故障根因记录）。

### 3.3 关键设计决策

| 设计项 | 方案 | 理由 |
|--------|------|------|
| 必填字段永不缺 | 数据缺失时编码为表 3 "未知"哨兵值 | 保证每个包格式合法、全程持续广播，满足 5.1.2 |
| 起飞/落地消抖 | 地面↔空中连续确认（300ms/500ms），紧急状态立即生效 | 防止信号抖动误判，满足 5.1.2 "全过程" |
| BLE 三级自愈 | 原地重启 → PHY 切换 → NimBLE 重初始化；全部失败红灯告警 | 满足 5.1.2 持续性要求，最大限度降低飞行中断风险 |
| USB 数据自恢复 | 连续 200 帧 CRC 失败 → 关闭重开 USB + 重置解析器（5s 冷却） | 防止数据流损坏后卡死 |
| USB 只读保护 | `out_buffer_size=0`，显式清除 DTR/RTS | 杜绝任何数据反向注入飞控，避免干扰飞控运行 |
| 时间戳防倒退 | 检测 boot_ms 回绕，过期字段清除标记编码为未知 | 防止时间倒退产生脏数据 |
| 飞行日志防丢 | 扇区对齐擦除 + 逐条写入 + CRC16 校验 | 修复"日志区只存 1 条"缺陷，坏数据可识别 |
| 看门狗兜底 | 覆盖 main/USB/日志/命令行四任务，5s 无响应自动复位 | 满足 GB 42590 看门狗要求（A.2.3.5.5） |
| 操作员位置三级回退 | HOME_POSITION → 起飞点 → 表 3 未知哨兵值 | 优先使用精确数据，逐级降级 |
| 纯 BLE 广播 | 仅占用 BLE 37/38/39 信道，不做 WiFi 广播 | 避免与公司编队 WiFi 控制抢信道 |

## 4. 测试验证

### 4.1 测试内容

**固件侧测试**——测的是固件里每一行涉及数据解析和报文编码的代码。因为这套固件直接在无人机上跑，一旦编码出错，广播出去的报文就不合规，而且固件更新后没法像服务器软件那样随时回滚，所以必须在发布前穷举验证。测试用真实飞行数据（1899 帧 .DAT）逐帧喂给解析器，对照手工计算的标准答案逐字节核对编码结果，还灌入粘包、丢字节、乱码等异常数据验证自愈能力。8303 例全部通过，0 失败。

**PC 检测软件测试**——测的是 `RIDCheck.exe` 里的解码和判定逻辑。因为 PC 软件和固件各自独立实现了一套相同的解码/判定代码，必须确认两边对同一包数据的解读完全一致，否则用户用 PC 软件看到的结论就和安卓 APP 不一致，现场验收会出矛盾。测试用例覆盖全部 21 个字段的解码、合规判定逻辑和 BLE 过滤，28 例全部通过。

**安卓检测 APP 测试**——测的是手机端从抓包、解码、判定到报告生成、时间轴的完整流程。安卓 APP 是现场验收的主要工具，它的判定结论必须和 PC 端完全一致。测试使用与 PC 端同一套标准答案，覆盖解码、合规判定、设备列表、报告生成、问题时间轴、会话统计等模块，63 例全部通过。

数据来源：8 份真实飞行串口日志（.DAT），经第三方 pymavlink 交叉核对确认。

### 4.2 测试规模

| 套件 | 用例数 | 覆盖范围 |
|------|:------:|----------|
| 固件侧测试（C++，PC 端运行） | **8303 例，0 失败** | 1899 帧真机数据逐帧解析；编码逐字节对照 golden 样本；粘包/丢字节/乱码/篡改数据自愈验证；状态机、飞行日志、故障记录全覆盖 |
| PC 检测软件（Python） | **28 例通过** | 字段解码、合规判定、BLE 扫描过滤——与固件解码口径一致 |
| 安卓检测 APP（Kotlin） | **63 例通过** | 解码、合规判定、设备列表、报告生成、时间轴、会话统计——与 PC 端共用同一套标准答案，行为一致 |

## 5. 真机验收与配套工具

### 5.1 真机验收

1. 模块 USB 口直连飞控，飞控开机即有数据，模块随解锁起飞自动切换广播状态
2. nRF Connect（安卓）抓包可正确接收以 `0x0D50` 开头的广播报文
3. 自研安卓 APP 现场抓包、逐字段解码，内置判定器给出"正常/警告/故障"结论，能够导出分析报告和广播日志。
4. 两路均稳定收到 400ms 间隔广播，21 字段解码与国标一致，全链路验证通过

### 5.2 配套检测工具

本项目配套了两套检测工具，分别用于电脑端和手机端。两套工具的解码逻辑和判定规则完全一致，可根据现场条件选择使用。

#### PC 检测软件（`RIDCheck.exe`）

注意，**只有LMP≥9、BLE达到5、win11以上电脑才能正常接受BLE信号**。早年电脑或者蓝牙卡版本较低的电脑无法接收到广播信号，这是电脑本身问题，并非软件问题。

软件界面分为两个标签页：

**标签页一：BLE 接收 / 解码 / 判定**

使用场景：在电脑旁对模块进行近距离验收。打开模块电源后，点击"开始扫描"，软件通过电脑蓝牙搜索周围所有正在广播的 RID 模块。发现设备后会显示设备名、MAC 地址、信号强度和已收到的包数。选中一个设备后，软件自动逐包解码并在界面上展示：

- **字段明细表**：国标 21 项字段逐项列出，直接显示可读的中文含义（如"运行类别：开放类"、"坐标系：WGS-84"），而不是原始十六进制数字
- **内置判定器**：自动给出"正常"（绿）、"警告"（黄）、"故障"（红）三级结论。检查内容包括：报文结构是否正确、唯一识别码格式是否合规（20 位、不含禁用字符）、实名登记号是否已替换默认值、位置/高度/速度是否在合理范围内、广播速率是否达标（国标要求 ≥1 包/秒）、数据是否新鲜（超过 2 秒未更新告警、超过 5 秒判故障）、内容是否冻结（连续 5 个相同包则警告数据源可能卡死）
- **原始数据包**：显示最近一包的完整十六进制内容，可直接复制

如果电脑的蓝牙不支持 BLE 5 扩展广播（部分老电脑会出现扫描不到设备的情况），可以用 nRF Connect 等第三方工具抓到原始广播帧，然后通过"粘贴 HEX 解码"功能，把十六进制数据粘贴进来，软件会自动提取有效载荷并完成解码和判定。

**标签页二：串口飞行日志提取**

使用场景：把模块内部存储的飞行日志导出为 CSV 文件进行分析。操作步骤：

1. 用 USB 线连接模块的 COM 口和电脑
2. 在软件中选择串口号（自动列出可用端口）和波特率（默认 115200）
3. 点击"导出飞行日志"，选择保存路径
4. 软件自动向模块发送导出指令，接收二进制记录并逐条解码
5. 导出完成后显示总记录数、CRC 校验失败数（如果有），并可一键打开输出目录

输出的 CSV 文件包含 25 列：记录序号、Flash 时间戳（毫秒 + UTC 时间）、国标全部 21 个字段（唯一识别码、实名登记号、运行类别、无人机分类、遥控站位置、无人机位置、航迹角、地速、相对高度、垂直速度、大地高度、气压高度、运行状态、坐标系、水平精度、垂直精度、速度精度、数据时间戳、时间戳精度等），以及每条记录的 CRC 校验结果（Y/N）。文件为 UTF-8 编码，可直接用 Excel 打开。

#### 安卓检测 APP（`RID检测` v1.7）

安卓 APP 面向**现场验收**场景设计——拿着手机到飞行场地，打开蓝牙扫一扫就能看到周围所有模块的广播内容和合规状态。

**主界面——设备列表**

点击"开始扫描"后，APP 实时搜索周围所有正在广播的 RID 模块。每发现一个设备就显示为一行（设备名 + MAC + 信号强度），点击即可进入该设备的详情页。支持同时扫描多个设备，各自独立统计。

另外提供"粘贴解码"功能：从 nRF Connect 等工具复制一段原始广播帧的十六进制内容粘贴进来，APP 自动解码并给出单包判定。这个功能不需要持续扫描，适合快速验证某个抓到的包。

**设备详情页**

进入后可以看到：

- **判定结论**：页面顶部醒目显示"正常"（绿）/ "警告"（黄）/ "故障"（红），附带广播速率和简要说明
- **问题列表**：每一条发现的问题都标明严重程度、对应的国标条款编号、具体描述和整改建议。如果没有问题则显示"未发现问题"
- **最新一包的全部字段**：21 项国标字段逐项以可读格式展示
- **信号与速率曲线**：双轴折线图，左轴显示信号强度（RSSI），右轴显示广播速率，横轴为时间。可以直观看到信号是否稳定、速率是否均匀
- **会话统计**：对整个扫描期间收到的所有数据进行统计——数值类字段显示范围（最小值~最大值）和均值；枚举类字段显示各选项占比（如"开放类 60%、特定类 40%"）；坐标类字段显示经纬度跨度和最大位移距离；精度字段显示"未知"占比
- **问题时间轴**：记录每个问题从出现到消失的完整时段（开始时间、结束时间、持续时长），可以回溯飞行过程中什么时候出了什么状况
- **原始数据**：最近一包的完整十六进制内容，支持复制和分享

**导出功能**

- **Word 合规报告**（8 章）：包含检测信息、被测设备信息、判定结论与问题表、异常事件记录（含运行状态时间轴如"地面→空中→紧急"）、全部 21 个字段的统计汇总表、信号质量与相对轨迹图、结论、免责声明。可直接用于现场验收存档
- **CSV 逐帧日志**：每收到一包记录一行，包含接收时间、信号强度、原始十六进制、全部 21 个解码字段值。UTF-8 编码，可直接用 Excel 打开

**后台常驻扫描**

扫描过程中切到其他 APP（如地面站软件），扫描不会中断。状态栏会显示"RID 检测 后台扫描中"的常驻通知。回到 APP 后所有数据还在。点击底部"退出"才会彻底停止扫描并关闭 APP。

**帮助页面**

APP 内置说明页面，介绍什么是运行识别、国标 21 项字段的含义、判定规则、使用步骤和免责声明，方便首次使用者快速了解。

## 6. 自研必要性

国标 GB 46750-2025 实施后，市面上能买到的 RID 模块主要有两款：华科尔 W-RID（约 ¥199）和 CUAV C-RID（约 ¥299）。我们实际购买了 W-RID 进行装机测试，并对 C-RID 进行了详细的线上调研。结论是**两者都无法满足我公司的实际需求**。

### 6.1 华科尔 W-RID（已购买实测）

W-RID是华科尔推出的远程广播模块，宣称支持 DroneCAN/USRT 接口、广播距离可达 3km，价格约 ¥199。

**接上就不能用。** W-RID 只能被华科尔自家的 WKGCS 地面站识别和检测，它的定位就是华科尔教培无人机生态的配套零件，不是一个通用模块。我们的飞控口就算插入W-RID，它也无法发出正常蓝牙广播。同时，WKGCS地面站完全无法控制我们的无人机。换句话说，W-RID 只认华科尔的飞控，别家的飞控插上就是废物。

**3km 广播距离严重存疑。** 华科尔宣传 W-RID 采用 BLE 蓝牙广播、覆盖距离 3 公里。但 BLE 5.0 在实际环境中的有效广播距离通常在几十米到一两百米之间，3km 远远超出 BLE 物理层的常规能力。怀疑其而很可能混用了 WiFi 链路。

**无法读取飞行日志。** 国标 5.1.8 明确要求能够从 RID 模块中读取其内部存储的飞行数据。我拿到 W-RID 后，翻遍了产品文档和华科尔官网，找不到任何关于日志读取方式的说明。既没有串口导出命令，也没有配套的上位机工具，这个国标要求完全没有被满足。

**合规性无据可查。** W-RID 没有公开其数据格式是否符合 GB 46750-2025，没有测试报告，没有认证记录，也没有像 C-RID 那样发布过任何关于 GB 支持的技术声明。我们在华科尔官网和论坛上能找到的关于 W-RID 的信息只有几句话的产品介绍，无法判断其报文格式、版本字节、字段编码是否按国标实现。买来后因为用不了，这一个合规性检测也不了了之。

**总结：实测不可用。** W-RID 的核心问题不在于某个参数不达标，而在于它从设计上就没打算让第三方使用。它是一个"配件"而非"产品"——只有搭配华科尔全套生态（F8 飞控 + WKGCS 地面站）才有意义。对于使用自研飞控的编队无人机来说，买回来装上就是不能用。

### 6.2 CUAV C-RID（线上调研，未购买）

C-RID 是当前知名度最高的国产 RID 模块，基于 ESP32 芯片，支持 WiFi + BLE 双链路广播，价格约 ¥299。我们未购买实物，但通过官方文档、产品页面和开源社区进行了详细调研。

**合规性无人兜底。** CUAV 官方文档明确声明："本方案仅为引导整机制造商实现强制国标，做技术分享，不对符合性提供任何保障……因符合性造成的任何后果由整机制造商自行承担。"换言之，如果用了 C-RID 但报文格式不合规，责任完全在整机厂，CUAV 不承担。

**生态绑定严重。** C-RID 深度绑定 CUAV 自家的飞控和地面站生态，要求刷入专用固件或使用其厂商无人机，才能配合地面站使用。我们的无人机无法接入 CUAV 的地面站，装上 C-RID 后飞控会被锁死。

**WiFi 广播与编队控制抢信道。** C-RID 采用 WiFi + BLE 双链路广播。我们公司的无人机编队表演普遍使用 WiFi 进行集群控制，C-RID 的 WiFi 广播会直接和编队控制信号争抢信道，可能导致编队通信延迟增大甚至丢包。

**无法读取飞行日志。** 与 W-RID 一样，C-RID 没有提供任何日志读取方式。

**GB 支持时间线存疑。** GB 46750 于 2025 年 5 月 1 日正式实施，C-RID 在 5 月 9 日就发布了"支持固件"。但 CUAV 中文官网的产品页至今仍引用旧国标 GB/T 41300-2022，未提及 GB 46750-2025；上游开源项目 ArduRemoteID 的 GB 46750 支持 issue（#158）至今未关闭。信息互相矛盾，对其实际合规程度存疑。

### 6.3 结论

两家竞品的共同问题是：**绑定自家生态、不开放兼容、不兜底合规、不提供日志读取**。这些障碍不是通过简单的适配或升级能解决的——它们的产品定位就是服务于自家无人机体系，天然排斥第三方接入。

## 7. 已知问题与量产准备

### 7.1 已知问题

| 编号 | 问题是什么 | 现状 | 需要做什么 |
|:----:|-----------|------|-----------|
| **P-1** | **网络式 RID 链路**：国标 5.1.1 要求整机同时具备"广播式 + 网络式"两条远程识别链路。广播式（BLE）本模块已实现；网络式指经 4G/蜂窝网络向民航局 UOM 平台实时报送飞行数据 | 网络式是否由量产机自带，**未确认** | 向整机厂确认：①量产机有无 4G 模块？②是否已向 UOM 报送实时位置/高度/航向/速度/UPIC？③报送链路是否整机自带？④实名登记与 UOM 注册是否出厂完成？ |
| **P-2** | **飞控交联**：国标 5.1.7 要求 RID 模块失效时能通知飞控——起飞前失效禁止起飞，飞行中失效触发悬停/返航/降落。模块与飞控之间需要一条通信链路来传递这些安全指令 | 当前仅有软件抽象接口（`IFcInterlink`），**未接入真实飞控**，实际发指令的能力未实现 | 确定量产后端方案：方案 A——独立模块经 UART 向飞控发 MAVLink/DroneCAN 指令；方案 B——逻辑合并进飞控固件直接调用内部接口。鉴于编队无人机特殊性，**此部分可暂缓** |
| **P-3** | **GPS 精度字段**：国标要求广播中包含定位精度因子（eph/epv），用于告知接收方当前 GPS 数据有多可信。该字段应由飞控从 GPS 模块读取后填入 | 实测 ArduPilot 飞控在 GPS 锁定（30+ 星）下 eph/epv 恒为 0，模块只能上报"未知"；**不是本模块的问题**，是飞控未填充该字段 | 推动飞控团队修复 GPS 驱动中精度字段的填充 |
| **P-5** | **广播辐射功率（EIRP）**：国标 6.1.3 对轻型无人机的 BLE 广播辐射功率有上限要求，需实测确认不超标 | 目前仅近距离验证了链路连通，**没搞 EIRP 实测** | 安排场地实测 |

## 8. 结论

### 8.1 当前状态

本项目已完成**原型验证阶段**的全部工作：

- **合规性**：GB 46750-2025 广播式 RID 要求逐项实现，21 项数据内容全部覆盖，核心条款（5.1.2 持续广播、5.1.3 间隔、5.1.5 指示灯、5.1.8 日志存储）均已满足
- **可靠性**：固件 8303 例 + 双端 APP 共 91 例自动化测试全部通过，真机验收链路打通
- **工具链**：PC + 安卓双端检测工具可用，支持现场验收与合规自查
- **自恢复**：BLE/USB/任务看门狗三级异常处理机制完备
