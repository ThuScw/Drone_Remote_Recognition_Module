## 一、致命缺陷：这些 bug 会让你的模块在天上或地上直接失效

### 1. NimBLE 与 Bluedroid API 混用 —— BLE 发射功率设置完全无效

```cpp
// ble_rid_broadcaster.cpp
esp_err_t txRet = esp_ble_tx_power_set(ESP_BLE_PWR_TYPE_ADV, BLE_TX_POWER_LEVEL);
```

**这是本项目的最大硬伤。** `esp_ble_tx_power_set()` 是 **Bluedroid 协议栈**的 API，而你的项目使用的是 **NimBLE**。在 ESP-IDF 中，这两个协议栈是互斥编译的，NimBLE 不会响应 Bluedroid 的功率控制调用。你读回的 `actualPwr` 只是 NimBLE 内部的默认值，你以为设到了 +9 dBm，实际可能只有 0 dBm。

**工程质问：**
- GB 46750-2025 第 6.1.3 条要求轻型无人机 EIRP ≥ 4 dBm，你有没有用频谱仪或至少 nRF Connect 的 RSSI 距离测试验证过实际发射功率？如果监管抽检功率不达标，整批货能不能退？
- NimBLE 的正确功率控制应通过 `ble_hs_hci_util_set_tx_pwr()` 或 `esp_ble_tx_power_set()` 仅在 Bluedroid 配置下有效，你的 `sdkconfig.defaults` 里 `CONFIG_BT_NIMBLE_ENABLED=y` 已经彻底堵死了这条路径。

**建议：** 立即改用 NimBLE 原生的 HCI 命令设置 TX power，并在 `selfTest()` 中加入 RSSI 回环验证（如果硬件支持）或至少文档化功率测试 SOP。

### 2. 飞行日志环形缓冲区读取逻辑在绕回后完全错误

```cpp
// flight_log.cpp
uint32_t oldestOffset = (total <= capacity) ? 0 : writeOff;
uint32_t physicalOffset = (oldestOffset + index * kRecordSize) % _partitionSize;
```

**这个公式在分区绕回后（overwrite 发生之后）是错的。** 当 `total > capacity` 时，你设 `oldestOffset = writeOff`，然后按 `writeOff + index * 96` 线性取模。这意味着你假设记录从 `writeOff` 开始**连续排列到分区末尾**，然后**无缝绕回到分区开头**。

但 Flash 的写入是**原地覆盖**的。实际情况是：最新的记录在 `writeOff - 96` 处，最旧的在 `writeOff` 处，中间可能有一段**已经被新数据覆盖的碎片区域**，以及一段**旧数据残留区域**。你的线性取模完全无视了这种非连续性，绕回后读出的"历史记录"大概率是错序的，甚至是被部分覆盖的损坏数据。

**工程质问：**
- GB 46750-2025 第 5.1.8 条要求存储不少于 120 小时，且"不可手动删除"。如果监管人员导出日志时，第 N 条和第 N+1 条的时间戳是倒序的，或者中间缺了 30 分钟，你怎么解释？
- 你的 `readRecord(index)` 接口承诺 "0=最旧, N-1=最新"，但绕回后这个语义根本不成立。你有没有用 Python 脚本做过 120 小时连续写入后的全量导出验证？

**建议：** 每条记录必须带**单调递增的序列号**（sequence number），读取时按序列号排序，而不是靠物理偏移量臆测顺序。或者改用更成熟的循环队列实现（如记录索引表）。

### 3. `portENTER_CRITICAL_SAFE` 内执行 MAVLink 解析 —— 实时性灾难

```cpp
// flight_data.cpp
void FlightDataSource::onUsbData(...) {
    portENTER_CRITICAL_SAFE(&_parserMux);
    for (size_t i = 0; i < data_len; i++) {
        mavlink_parseByte(_parser, data[i], nowMs);  // CRC-16 计算 + 状态机
    }
    portEXIT_CRITICAL_SAFE(&_parserMux);
}
```

USB Host 的数据回调是在**中断上下文或高优先级任务**中执行的。你把整个 MAVLink 帧解析（包括 CRC-16/MCRF4XX 计算、状态机跳转、消息分发）全部塞进了临界区。ESP32-S3 是双核 MCU，临界区会关中断或锁总线，这意味着：

- 你的 BLE 广播定时、RMT LED 驱动、甚至飞控的 USB 时序都可能被这个临界区**延迟数十到数百微秒**；
- 如果飞控一次批量发送 512 字节 MAVLink 数据（这在 ArduPilot 日志下载或参数同步时很常见），你会在临界区里执行几百次 CRC 计算，**直接触发看门狗或导致 BLE 广播丢包**。

**工程质问：**
- 你的主循环看门狗设了 5 秒，但如果 USB 回调把中断关了 10ms，BLE 的 100ms 广播间隔会不会出现 jitter？监管要求的 ≤1s 广播间隔是**硬实时约束**，不是平均约束。
- 你有没有用逻辑分析仪抓过 BLE 广播的实际间隔分布？还是只看 `ESP_LOGI` 的自我安慰？

**建议：** 临界区只保护**状态变量的原子更新**（如 `bufferIdx`、`state`），把 CRC 计算和消息解码移到任务上下文。最简单的做法：USB 回调只做 `xQueueSendFromISR()` 把原始字节丢给解析任务，解析任务在主循环或独立任务中执行。

## 二、严重隐患：这些设计在量产中会爆炸

### 4. 内存泄漏与不可回收对象

```cpp
// main.cpp
manager = new RIDBroadcastManager(broadcaster, flightLog, statusLed, interlock);
// 永远没有 delete

// console_cmd.cpp
auto* self = new ConsoleCmd();  // 泄漏，且无法后续访问
```

嵌入式系统不是桌面应用，**`new` 而不 `delete` 不是"反正不关机"的借口**。ESP32-S3 的 heap 只有几百 KB，如果你的模块支持 OTA 或动态重配置，这些泄漏会累积。更关键的是，`RIDBroadcastManager` 持有大量状态，如果 `init()` 失败后重试，你会重复 `new` 出多个实例。

**建议：** 全部改用静态分配或 `std::aligned_storage`，禁止在飞行固件中使用裸 `new`。`ConsoleCmd` 应作为单例静态成员，而不是堆分配。

---

### 5. `FlightLog` 自旋锁用于任务间同步 —— 愚蠢的忙等待

```cpp
// flight_log.cpp
portENTER_CRITICAL_SAFE(&_spinlock);
_writeOffset += kRecordSize;
_recordCount++;
portEXIT_CRITICAL_SAFE(&_spinlock);
```

`_spinlock` 是 `portMUX_TYPE`，`portENTER_CRITICAL_SAFE` 在任务上下文中会**关中断**。你的 `logTaskLoop` 是一个 FreeRTOS 任务（优先级 1），而 `readRecord` 可能被 `console_cmd` 任务（优先级 1）或主任务调用。用关中断来保护 `_writeOffset` 和 `_recordCount` 的读写，相当于：

- 每次写 Flash（已经够慢了）还要额外关中断几微秒；
- 如果 `readRecord` 被高优先级任务调用，它会直接关中断读 Flash，**阻塞整个系统的任务调度和中断响应**。

**工程质问：** 你为什么不用 `SemaphoreHandle_t` 或 `pthread_mutex_t`？ESP-IDF 提供了完整的 FreeRTOS 同步原语，自旋锁是给**中断处理程序**或**极短临界区**用的，不是给 Flash I/O 这种毫秒级操作用的。

**建议：** 全部替换为 `xSemaphoreTakeRecursive()`，并确保 `readRecord` 和 `writeRecord` 不会死锁。

### 6. 气压高度被错误地赋值为大地高度

```cpp
// mavlink_parser.cpp
fd.baroAlt = p.altMsl;  // ????
```

`altMsl` 是 GPS 椭球高或 AMSL（平均海平面高），`baroAlt` 是气压计高度。两者在物理上完全不同，差个几十米很正常。你把 GPS 高度填进了气压高度字段，这在 GB 46750-2025 的数据语义上是**造假**。

**建议：** 如果飞控没有发送 `SCALED_PRESSURE` 或类似消息提供气压高度，应该将 `baroAlt` 标记为无效（`validMask` 不置 `FLD_BARO_ALT` 位），而不是用错误数据填充。

### 7. 三级自修复的"降级"状态没有对外暴露

```cpp
// broadcast_manager.cpp
if (result == BleRidBroadcaster::RecoveryResult::DEGRADED) {
    // Tier 2/3 恢复后标记为 degraded，但广播继续
}
```

Tier 2（切换 PHY 到 Coded）和 Tier 3（完整 NimBLE 重初始化）都被标记为 `DEGRADED`，但 `isDegraded()` 方法只在 `BleRidBroadcaster` 内部，**没有传递到 `RIDBroadcastManager` 或联锁逻辑**。这意味着：

- 模块可能在 Coded PHY（125 kbps，范围大但发现慢）上运行，但飞控和操控员完全不知情；
- 如果 Tier 3 重初始化后广播恢复，但 MAC 地址可能改变（如果 NimBLE 重新随机化），你的 UAS_ID 虽然不变，但接收方 App 可能把它当成新设备。

**建议：** `DEGRADED` 状态必须触发 LED 闪烁模式变化（如黄灯）或联锁告警，且重初始化后应固定使用 Public Address，避免 MAC 漂移。

## 四、架构质疑：这些设计选择暴露了对嵌入式安全的误解

### 11. "空中不拉闸、地面拉闸"的联锁逻辑过于简单

```cpp
if (isAirborne()) {
    // 空中故障只告警不拉闸
} else {
    _interlock.disarm();  // 地面拉闸
}
```

这个逻辑基于 `_lastValidData.opStatus`，但 `opStatus` 本身来自 MAVLink `HEARTBEAT` 的 `base_mode` 位。如果飞控在**起飞瞬间**（刚刚离地 10cm）MAVLink 数据丢失，`_lastValidData` 会保留 `STATUS_AIRBORNE`，此时如果 BLE 故障触发 self-heal 失败，模块认为自己在空中，**不拉闸**，但飞控可能已经因为 MAVLink 超时进入了 Failsafe 降落模式。联锁的语义和飞控的实际状态可能完全脱节。

**建议：** 联锁决策应引入**多源融合**（如 GPS 高度、空速、电机转速），而不是单一依赖 MAVLink 状态字。或者至少，地面→空中的状态转换应要求**连续收到 GPS 高度 > 2m + 地速 > 1m/s**，而不是只看 `HEARTBEAT` 的 armed 标志。

---

### 12. 时间戳漂移问题被完全忽视

```cpp
fd.unixTimestampMs = (uint64_t)p.unixBootOffsetMs + p.lastPositionBootMs;
```

`unixBootOffsetMs` 是 `SYSTEM_TIME` 消息到达时计算的 `unixTime - bootMs`。但 `bootMs` 是飞控的单调时钟，ESP32 的 `nowMs` 也是单调时钟，**两者的漂移率不同**（石英晶振误差 ±20ppm ~ ±50ppm）。连续飞行 2 小时后，这个公式算出的时间戳可能与实际 UTC 时间偏差 **144ms ~ 360ms**，超过 GB 46750 的精度要求。

**建议：** 定期（如每 30 秒）重新同步 `unixBootOffsetMs`，并在 `SYSTEM_TIME` 长时间未更新时将 `tsAcc` 降级。

---

### 13. `config.h` 里的硬编码密钥/ID 是量产灾难

```cpp
#define UAS_ID "CPNYMDL001234567890A"
#define REALNAME_ID "00000000"
```

这些宏在编译时固化进固件，意味着**每一台无人机烧录的固件都不同**（因为 UAS_ID 必须唯一）。你没有提供任何量产烧录工具（如基于 esptool 的批量写入脚本），也没有 NVS 动态配置接口。工厂工人需要为每一台设备改 `config.h` 重新编译？这不可扩展。

**建议：** UAS_ID 和 REALNAME_ID 应存储在 NVS 或 eFuse 自定义字段中，量产时通过烧录工具单独写入，固件统一编译。

## 问题 1：GPIO 联锁引脚从未被实际驱动 —— "联锁"功能完全是文档虚构

```cpp
// config.h
#define INTERLOCK_RID_OK_GPIO  GPIO_NUM_6   // 飞控联锁

// indicators.cpp
void RIDInterlock::arm() {
    _armed = true;
    if (_sendCb) { _sendCb(true); }  // 只发 MAVLink，不动 GPIO
}
void RIDInterlock::disarm() {
    _armed = false;
    if (_sendCb) { _sendCb(false); } // 只发 MAVLink，不动 GPIO
}
```

**全项目搜索 `gpio_set_level`、`gpio_config`、`gpio_pad_select_gpio`，没有任何一处操作 `GPIO_NUM_6`。**

这意味着：无论模块自检通过还是故障，GPIO6 永远处于**高阻态/默认电平**。飞控端的 RID_OK 输入引脚如果内部有弱上拉，它永远看到高电平；如果有弱下拉，永远看到低电平。你的"空中不拉闸、地面拉闸"安全策略，在物理层上**完全不存在**。

**工程质问：**
- 如果监管抽查时把模块从飞控上拔下来，用万用表量 GPIO6，发现无论故障与否都是高阻态，你怎么解释 GB 46750-2025 第 5.1.7 条的符合性？
- 你的工厂测试工位（ICT/FCT）有没有对联锁引脚做高低电平扫描？如果没有，产线上 1000 台设备里哪怕有 1 台因为虚焊导致 GPIO6 悬空，你靠什么筛出来？

**建议：** 立即补全 `RIDInterlock` 的 GPIO 驱动逻辑（`gpio_config` + `gpio_set_level`），并在 `init()` 中配置为推挽输出+上拉，默认拉低。产线必须增加联锁引脚电平自动测试项。

## 问题 2：广播时间戳与发送成功解耦 —— BLE 故障时实际广播间隔可能远超 1s

```cpp
// broadcast_manager.cpp
void RIDBroadcastManager::handleBroadcast(uint64_t nowMs) {
    if (!_broadcastActive) return;
    if (nowMs - _lastBroadcastMs < BROADCAST_INTERVAL_MS) return;

    _lastBroadcastMs = nowMs;   // ← 先记账
    _broadcastCount++;

    // ... 新鲜度检查 ...

    if (!_broadcaster.updateBroadcastData(_currentPacket)) {
        ESP_LOGW(TAG, "Broadcast data update failed");
        // ← 发送失败，但 _lastBroadcastMs 已经更新了！
        return;
    }
}
```

这里 `_lastBroadcastMs` 在**调用 `updateBroadcastData` 之前**就被更新了。如果 BLE 控制器此时正忙（NimBLE 的 `ble_gap_ext_adv_set_data` 返回 `BLE_HS_EBUSY`），这次广播会静默失败，但系统认为"已经广播过了"，于是**再等 800ms 才尝试下一次**。如果连续失败 3 次触发 self-heal，self-heal 本身又需要数百毫秒，**实际两次成功广播的间隔可能达到 3~5 秒**，直接违反 GB 46750 ≤1s 的硬约束。

**工程质问：**
- 你有没有用 nRF Sniffer 或逻辑分析仪抓过 BLE 广播的实际间隔分布？还是只看 `ESP_LOGI` 的"TX #1234"自我安慰？
- 在电磁干扰环境（如高压线附近、多机编队），BLE 更新失败的概率是多少？你的 800ms 间隔在 95 百分位下还能保持吗？

**建议：** 维护两个时间戳：`_lastBroadcastAttemptMs`（调度用）和 `_lastBroadcastSuccessMs`（合规监控用）。只有 `updateBroadcastData` 返回 true 时才更新成功时间戳。如果 `_lastBroadcastSuccessMs` 与 `nowMs` 差值超过 1s，立即触发紧急状态上报。

## 问题 3：Flash 擦除关中断 —— 日志写入会"冻结"BLE 广播和 USB 接收

```cpp
// flight_log.cpp
uint16_t FlightLog::writeRecord(...) {
    esp_err_t rc = wl_erase_range(_wlHandle, _writeOffset, kRecordSize); // ← 擦除 4KB sector
    // ...
    rc = wl_write(_wlHandle, _writeOffset, record, kRecordSize);
}
```

`wl_erase_range` 底层调用 `spi_flash_erase_range`，在 ESP32-S3 上擦除一个 4KB sector 需要 **20~40ms**。在此期间，ESP-IDF 默认会**关闭 CPU 缓存和中断**（`CONFIG_SPI_FLASH_YIELD_DURING_ERASE` 虽可 yield，但在 `portENTER_CRITICAL_SAFE` 保护的临界区内无法 yield）。

你的 `writeRecord` 被 `logTaskLoop` 调用，而 `logTaskLoop` 运行在优先级 1 的任务。更致命的是，`readRecord`（被 `console_cmd` 任务调用）和 `writeRecord` 都用同一个 `_spinlock` 保护：

```cpp
portENTER_CRITICAL_SAFE(&_spinlock);  // ← 关中断
_writeOffset += kRecordSize;
_recordCount++;
portEXIT_CRITICAL_SAFE(&_spinlock);
```

但 `wl_erase_range` 在**临界区外**调用，这本身没问题。问题在于：**如果 `writeRecord` 正在执行 `wl_erase_range`，此时 USB Host 中断来了，数据无法及时处理；或者 BLE 广播定时到了，`updateBroadcastData` 被调用，但 NimBLE 需要中断来驱动 HCI，中断被延迟会导致 BLE 控制器复位**——而这又会触发你的三级 self-heal，形成**"写日志 → 关中断 → BLE 复位 → self-heal → 恢复广播 → 再过 10s 写日志 → 又复位"**的周期性故障。

**工程质问：**
- 你有没有在开启飞行日志的情况下，用示波器量过 BLE 广播的 jitter？在日志写入瞬间，广播间隔的方差是多少？
- 如果无人机在 10Hz 振动环境飞行（多旋翼常见），Flash 焊点虚焊导致擦除时间波动到 100ms，你的看门狗会不会误触发？

**建议：** 
1. 将 `FLIGHT_LOG_TASK_PRIO` 设为最低（`tskIDLE_PRIORITY`），并确保 `wl_erase_range` 在独立任务中执行，与广播任务错开时隙；
2. 或者改用 **eMMC/SD 卡** 存储日志，彻底避开 Flash 擦除中断问题；
3. 最现实的方案：在 `handleBroadcast` 中检测 `_lastBroadcastSuccessMs`，如果日志写入导致广播延迟超标，临时跳过本次日志写入（丢日志不丢合规）。

## 问题 4：MAVLink v2 签名未处理 —— 安全飞控配置下解析器直接雪崩

```cpp
// mavlink_parser.cpp
p.expectedLen = headerLen + p.payloadLen + MAVLINK_V2_CRC_LEN;  // ← 只算到 CRC，没算签名
```

MAVLink 2 规范中，如果飞控启用了 **Message Signing**（`MAVLINK_SIGNING_FLAG_SIGN_OUTGOING`），每帧会在 CRC 之后附加 **13 字节的签名**（`link_id(1) + timestamp(6) + signature(6)`）。你的 `expectedLen` 只计算到 CRC（2 字节），所以：

1. 解析器收到带签名的帧后，在 CRC 处停止，把 13 字节签名当成**下一帧的 STX**；
2. 签名字节里大概率没有 `0xFD` 或 `0xFE`，解析器进入 IDLE，然后丢弃后续所有字节直到遇到下一个合法的 STX；
3. 这表现为**连续 CRC 错误**，触发你的 `MAVLINK_CONSECUTIVE_CRC_LIMIT`（200 次），进而触发 USB 恢复；
4. USB 恢复关闭再打开 CDC-ACM，飞控重新枚举，但签名仍然开着，于是**无限循环恢复**。

PX4 和 ArduPilot 在**安全飞行模式**（如 `SYSID_ENFORCE`）或**GCS 链路加密**场景下默认启用签名。你的模块在这些飞控上**完全无法工作**。

**工程质问：**
- 你的"已确认飞控 VID/PID"列表里，有没有测试过启用了 MAVLink 2 signing 的 PX4 v1.14+？
- 如果客户用的飞控固件是定制版，开启了签名，你的模块会不会在起飞后 30 秒内触发 USB 恢复，导致广播中断？

**建议：** 在 `mavlink_parseByte` 的 CRC 校验通过后，检查 `incompat_flags` 的 `MAVLINK_IFLAG_SIGNED` 位（bit 1）。如果置位，跳过 13 字节签名再继续解析。或者更简单地，在 `expectedLen` 中加上 `((incompat_flags & 0x01) ? 13 : 0)`。

## 问题 5：精度"兜底"逻辑实质是数据造假

```cpp
// broadcast_manager.cpp
uint8_t horizAcc = gb46750_mapHorizAcc(fd.horizAccM);
uint8_t vertAcc = gb46750_mapVertAcc(fd.vertAccM);
if (horizAcc == 0) horizAcc = HORIZ_ACC;   // ← 把"未知"改成"<10m"
if (vertAcc == 0) vertAcc = VERT_ACC;      // ← 把"未知"改成"<3m"
```

`gb46750_mapHorizAcc` 在 `ephM <= 0` 时返回 `0`，而 GB 46750-2025 中 `0` 的语义是 **"未知或不可用"**。你的代码把"未知"强制替换成了配置文件里的固定值（`<10m`、`<3m`），这意味着：

- GPS 完全失效时，你向监管系统报告"水平精度 <10m"；
- 如果此时无人机实际位置偏差了 500m（GPS 漂移），接收方 App 会基于你报告的 <10m 精度画一个极小的置信圆，**严重误导空管和其他飞行器**。

这在民航术语里叫 **"发布虚假导航精度信息"**，在多数国家是刑事犯罪。

**工程质问：**
- 如果监管方用模拟器注入 `eph=0`（GPS 失锁）的场景测试你的模块，你会不会被判为不合格？
- 你的 `HORIZ_ACC` 配置值有没有经过 RTK 基准站或 CORS 网的实际校准？还是拍脑袋写的 10？

**建议：** 删除这两行兜底逻辑。`horizAcc == 0` 时就该传 `0`（未知）。如果 GB 46750 要求 M 字段必须存在，你已经通过 `dataId` 置位满足了"存在"的要求，值填 `0` 完全符合标准语义。

## 问题 6：NimBLE reinit 存在 use-after-free 和任务泄漏

```cpp
// ble_rid_broadcaster.cpp
bool BleRidBroadcaster::reinitNimble() {
    nimble_port_freertos_deinit();  // ← 删除 host task
    vTaskDelay(pdMS_TO_TICKS(200));

    if (s_syncSemaphore) { vSemaphoreDelete(s_syncSemaphore); }  // ← 删除信号量
    s_syncSemaphore = xSemaphoreCreateBinary();  // ← 新建信号量

    nimble_port_freertos_init(host_task);  // ← 新建 host task
    // ...
}
```

这里有两个工程噩梦：

1. **use-after-free**：`nimble_port_freertos_deinit()` 只是向 host task 发送停止信号，但 task 的**实际删除是异步的**。如果 host task 在 200ms 内没删干净（比如它正在处理一个 HCI 事件），`vSemaphoreDelete(s_syncSemaphore)` 会删除一个**仍在被 host task 引用**的信号量。随后 `xSemaphoreGive(s_syncSemaphore)` 在 `on_sync` 中操作已释放内存，**行为未定义**（可能硬 fault，可能静默 corruption）。

2. **任务句柄泄漏**：`nimble_port_freertos_init(host_task)` 每次都会创建一个新的 host task，但旧的 task 句柄没有保存，你也无法删除它。如果 Tier 3 自修复在飞行中触发多次（比如电磁环境恶劣），FreeRTOS 的任务控制块（TCB）会不断累积，最终耗尽 RAM。

**工程质问：**
- 你有没有在压力测试（如连续 1000 次 BLE 复位）后检查 `uxTaskGetNumberOfTasks()` 的返回值？它是不是单调递增的？
- 如果无人机在高压输电塔附近飞行，BLE 频繁受干扰触发 Tier 3 恢复，10 分钟后会不会因为任务泄漏导致 `os_msys_get_pkthdr` 返回 NULL，广播彻底停止？

**建议：** 
- 在 `reinitNimble` 前用 `eTaskGetState` 确认旧 host task 已彻底删除；
- 或者更安全的做法：**禁止在飞行中执行 Tier 3 重初始化**。Tier 3 只应在地面维护模式下由人工触发，空中故障应直接进入 `FAULT` 状态并持续广播最后一包已知数据（GB 46750 允许"失效但持续发送"）。

## 问题 7：Python 导出工具的串口协议没有校验和、没有重传、没有流控

```cpp
// console_cmd.cpp
printf("+OK %lu\r\n", (unsigned long)available);
// ... fwrite 96*N bytes ...
printf("+DONE\r\n");
```

`flight_log_dump.py` 通过 UART0（115200 波特率）接收二进制数据。这个协议：

- 没有 CRC：如果 UART 在 6 分钟传输中受到电磁干扰（无人机电机、电调都是强干扰源），出现 1bit 翻转，Python 端**无法检测**；
- 没有流控：ESP32 端 `fwrite` 到 `stdout` 是阻塞的，但如果 PC 端 USB-串口芯片（如 CH340）的缓冲区满，数据会**静默丢失**；
- 没有重传：如果某条记录损坏，Python 脚本只标记 `CRC有效=N`，但不会要求重传，监管人员拿到的 CSV 就是残缺的。

在真实执法场景中，监管人员可能在**机库外、寒风中、用笔记本**导出日志。USB 线长 3 米、电机未完全断电、笔记本电池低电量导致 USB 供电不稳，这些因素都会提高误码率。

**工程质问：**
- 你有没有计算过 115200 波特率、3 米 USB 线、未屏蔽环境下，43200 条记录（约 4.1MB）的**预期误码率**？如果误码率是 1e-6，期望丢 33 字节；如果是 1e-5，期望丢 330 字节。你丢得起吗？
- 如果监管人员导出的 CSV 里有 3 条记录的时间戳是 1970-01-01（因为 UART 误码导致 timestampMs 被篡改），这份证据在法庭上有没有效力？

**建议：** 
1. 在二进制协议中加入 **XMODEM-CRC** 或 **SLIP + 每包 CRC32**；
2. 每条记录后加 `ACK/NAK` 握手，NAK 时 ESP32 重传；
3. 或者改用 **USB Mass Storage 模式**（ESP32-S3 支持 USB OTG MSC），把 flight_log 分区模拟成 U 盘，让 PC 直接读取文件系统，彻底避开串口协议的可靠性问题。
